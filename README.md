# cpp-modules-env

Окружение и шаблон для проектов на C++ под NixOS: `import std;` вместо
`#include`, clang в роли компилятора и полная стандартная библиотека от gcc.

## Новый проект

```sh
mkdir myproj && cd myproj
nix flake init -t github:is0ly/cpp-modules-env --refresh
direnv allow
just run
```

## Из чего собрано и почему

Связка нетипичная: **clang 21 + libstdc++ от gcc 15**. Причина в том, что
ни одна из привычных пар не даёт всего сразу.

- g++ с libstdc++ — модуль стандартной библиотеки собирается, библиотека
  полная, но BMI получается в формате gcc, а clangd его не читает: редактор
  теряет дополнение и переход к определению.
- clang с libc++ — редактор живой, но библиотека отстаёт: в libc++ 21 нет
  ни `fold_left`, ни `enumerate`, ни `zip`, ни `concat`.
- clang с libstdc++ — компилятор и clangd одной версии, формат BMI родной,
  библиотека при этом gcc-шная, со всеми свежими ranges. Плюс ABI совпадает
  с остальным nixpkgs, так что сторонние C++-библиотеки линкуются нормально.

Третий вариант держится на том, что clang способен скомпилировать модульный
исходник libstdc++ (`bits/std.cc`). Это не заявлено официально нигде —
проверено вручную и работает.

## Модуль std

Собирается рецептом `std-module`, от которого зависят `build`, `check` и
`tidy`. Два нюанса, без которых ничего не выйдет:

- **`-x c++-module`** — файл называется `std.cc`, и по расширению clang за
  модуль его не считает.
- **`-isystem$GCC_CXX_INCLUDE/backward`** — `std.cc` подключает `<strstream>`
  и другие устаревшие заголовки, которые libstdc++ держит в отдельном
  каталоге. Драйвер clang про этот каталог не знает.

Ещё одно требование — `hardeningDisable = [ "fortify" ]` в `shell.nix`. При
включённом `_FORTIFY_SOURCE` glibc подменяет `printf` и родню на inline-
обёртки с внутренней связанностью, а экспортировать такое из модуля нельзя.

Путь к заголовкам libstdc++ не прописан, а спрашивается у компилятора при
входе в шелл: store-путь меняется при каждом обновлении nixpkgs.

Пересборка модуля происходит при смене компилятора или флагов — и то и
другое пишется в `build/.toolchain` и сверяется. Разъезд флагов между BMI и
кодом clang не прощает.

## clangd

`compile_flags.txt` генерируется при входе в шелл. Важная тонкость формата:
**каждая строка файла — это один целый аргумент**, а не строка для разбора
шеллом. Поэтому `-isystem` пишется слитно с путём. С пробелом путь
получается с ведущим пробелом внутри, и заголовки молча не находятся.

Строка `-fmodule-file=std=$PWD/build/std.pcm` — то, ради чего всё
затевалось: она объясняет clangd, что такое `import std;`. Отсюда
особенность: **в свежем проекте редактор будет ругаться, пока не пройдёт
первая сборка**, потому что `.pcm` до неё не существует. После `just clean`
то же самое.

## Рецепты

- `fmt` — clang-format по `src`, nixfmt по флейкам
- `std-module` — BMI стандартного модуля (сам по себе нужен редко)
- `check` — синтаксис с `-Werror`, без сборки
- `tidy` — clang-tidy
- `build` / `run` / `debug` (gf2) / `gdb` / `memcheck` / `clean`
- `all` — fmt, check, build

## Свои модули

Шаблон рассчитан на один готовый модуль — `std`. Как только появятся свои
`.cppm`, «все файлы одной командой» в `build` кончится: понадобится порядок
сборки интерфейсов и `-fmodule-file` для каждого.

## Структура репозитория

```
flake.nix
README.md
template/
  flake.nix
  shell.nix
  justfile
  .clang-format
  .envrc
  .gitignore
  src/main.cpp
```

Файлы шаблона обязаны лежать в `template/` — на этот путь ссылается
`templates.default` в корневом флейке.

## Разово, без создания проекта

```sh
nix develop github:is0ly/cpp-modules-env
```
